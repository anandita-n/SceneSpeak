# Build plan

1. **Core generation loop** ✅ — photo → BLIP caption → LLM-generated vocabulary (`/generate-board`).
2. **RAG grounding** ✅ — curated AAC scenario word sets (playground, mealtime, classroom, bathroom, transition, social), embedded into ChromaDB; the most relevant entries are retrieved per scene and combined with a per-child history table (SQLite) so vocabulary stays consistent across a child's boards over time.
3. **Symbol mapping** ✅ — each generated word is mapped to a real ARASAAC pictogram via their public API, with a relevance-scoring layer on top (ARASAAC's raw search isn't ranked by relevance, so a naive "first result" pick returned wrong symbols for phrases — e.g. "all done" matched "garden" — fixed by only trusting a result when the query and one of its own keywords actually overlap). Words with no good match degrade gracefully to text-only rather than showing a wrong symbol.
4. **Verification layer** ❌ removed — a CLIP image–text similarity filter on "object" words, tuned to 0.23 on a 21-pair *synthetic* test set (90.9% precision there). On real photos it rejected clearly visible objects (desk, chair, book, pencil) and scored an absent "spoon" above a present "hand", so it did more harm than good. Replaced by giving Gemini the photo itself (step 9); Edit mode is the human safety net, as in QuickPic.
5. **Speech + persistence** ✅ — tap-to-speak via a server-side gTTS endpoint (`app/tts.py`, `GET /tts`) so every device hears the same consistent voice — each word is synthesized once and cached to disk as an MP3, with the browser's Web Speech API as a fallback if the backend can't produce audio; full board records (photo + caption + generated vocabulary) are now persisted per child (`app/boards.py`), not just vocabulary words, so past boards can be reopened.
6. **Frontend** ✅ — a multi-view UI (`static/`) served by FastAPI, matching a real AAC-app structure: Home → Create a Board → generated board (photo and symbol board side by side, like a real communication board layout) → My Library (past boards as a photo grid, click to reopen). A lightweight Edit mode lets a caregiver remove a wrongly-suggested tile before use. Tested end-to-end in-browser: navigation between all four views, board rendering with real ARASAAC image URLs, edit-mode toggle actually revealing and functioning remove buttons, and the empty-library state.

7. **QuickPic-style generation** ✅ — switched to QuickPic AAC's (Yu et al., 2024) per-part-of-speech generation: pronouns, verbs, prepositions, descriptors, objects, rendered as modified Fitzgerald Key columns. Dropped the uncited hand-made core list — core vocabulary belongs on the child's main device in fixed positions, not regenerated per photo — so RAG now retrieves only scenario word sets plus the child's history. Boards saved before the switch still load (their `core` words render in a legacy column).

8. **Server-side key + daily limit** ✅ — the Gemini key lives on the server (`.env`), the UI hides the key field when it's set, and `DAILY_BOARD_LIMIT` caps boards per day on that key (`app/usage.py`, atomic SQLite counter; failed generations don't count). Gemini quota and invalid-key errors are mapped to clear user-facing messages (429 / 401) instead of a raw 502.

9. **Multimodal generation + bigger word sets** ✅ — Gemini now receives the photo itself alongside BLIP's caption (as Zastudil et al. 2024 did with GPT-4V), with JSON-mode output. BLIP decoding fixed (`no_repeat_ngram_size`, fewer beams: 5.5s → ~3.5s, no more looping captions). Scenario word sets expanded from 53 entries / 6 scenarios to ~800 entries / 36 scenarios, so retrieval actually has to narrow the corpus. BLIP + RAG index warm up at startup.

10. **Evaluation** ✅ — `scripts/evaluate_rag_consistency.py` on 14 photos × 3 runs × 3 conditions: RAG raises the share of words from the curated AAC sets (59.1% → 64.9%) but not run-to-run consistency (0.731 → 0.724); child history is what drives consistency (0.724 → 0.960). Also caught and fixed an occasional malformed-JSON reply from Gemini (retry once).

Still open: Docker + deployment somewhere demoable.

Build in this order — there's a working, demoable thing after step 1.
